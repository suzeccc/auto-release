# README 优化参考

## 目标

把仓库根目录的 `README.md` 设计成面向主要读者的项目入口，而不是技术资料堆积页。README 的内容比例必须由项目类型、主要读者和首要任务决定，不使用适用于所有项目的固定比例。

## 工作流

1. **读取事实**
   - 读取现有 `README.md`、许可证、项目清单、入口配置、主要页面或模块、测试命令和 `docs/`。
   - 查找真实存在的 Logo、截图、演示图、架构图和小程序码。
   - 用运行结果、配置和代码验证项目能力；不把计划功能写成已完成功能。

2. **确定读者**
   - 根据入口、清单、文档、界面和发布方式识别项目类型。
   - 明确主要读者、次要读者，以及两类读者访问 README 时最需要完成的任务。
   - 区分产品使用者、集成开发者、部署运维者、贡献者和项目维护者，不把所有技术读者统称为“开发者”。
   - 无法可靠判断时，优先服务能够直接使用或集成项目的人，再服务贡献和维护人员。

3. **重组信息**
   - 按“主要读者最关心的信息 → 成功使用项目的最短路径 → 进阶配置 → 贡献与维护”排序。
   - 消费级应用、小程序和网站优先展示产品价值、界面、核心功能、使用流程与边界。
   - 库、SDK 和组件优先展示适用场景、安装、最小可运行示例、核心 API 与兼容性。
   - CLI 和运维工具优先展示安装、典型命令、输入输出、配置、权限与故障处理。
   - 框架和基础设施项目优先展示架构定位、快速开始、部署模型、兼容矩阵与运维边界。
   - 内部项目按实际角色优先级安排部署、运维、使用和开发内容。
   - 将数据库索引、完整 API、内部安全检查、长篇故障排查和详细联调步骤移入 `docs/`，README 只提供摘要与链接。

4. **编辑 README**
   - 保留仓库真实的品牌名称、许可证、致谢和必要兼容说明。
   - 使用短段落、表格、列表和一条清晰主线，避免重复标题、营销空话和大段原始日志。
   - 命令必须可复制；Windows 专用命令和跨平台命令要明确区分。
   - 图片必须有替代文本，尺寸和数量应克制，首屏避免被大量徽章占满。
   - 按“徽章决策”判断是否添加 Shields.io 徽章，不把徽章作为必选装饰。

5. **验证**
   - 运行 `git diff --check -- README.md`。
   - 检查所有相对链接和本地图片目标存在。
   - 检查徽章图片 URL 与点击目标有效，徽章内容与真实数据源一致。
   - 对照项目清单验证安装、启动、测试和构建命令。
   - 确认状态表与实际实现、联调结果和部署状态一致。
   - 仅修改文档时，不必运行完整代码测试；需在结果中明确说明。

## 项目类型与内容重心

以下比例仅用于帮助判断内容重心，不是硬性模板：

| 项目类型 | 主要内容 | 常见参考比例 |
|---|---|---|
| 消费级应用、小程序、网站 | 产品价值、界面、功能、使用流程 | 使用者 60%～80%，开发与维护 20%～40% |
| 开源桌面或移动应用 | 使用体验、安装、兼容性、贡献 | 使用者 50%～70%，开发与维护 30%～50% |
| 库、SDK、组件库 | 安装、示例、API、兼容性 | 集成使用 70%～90%，维护贡献 10%～30% |
| CLI、运维工具 | 安装、命令、配置、示例、故障处理 | 操作使用 60%～80%，开发维护 20%～40% |
| 框架、基础设施 | 快速开始、架构、部署、运维边界 | 技术使用 80%～90%，内部维护 10%～20% |
| 内部项目 | 按实际使用、部署、运维和开发角色确定 | 不设默认比例 |

同一项目存在多个读者群时，优先保证主要读者的最短成功路径，再为其他读者提供清晰入口或链接。

## 徽章决策

使用 [Shields.io](https://shields.io/) 生成简洁、一致且可读的徽章。徽章必须帮助目标读者快速判断项目状态，不以数量衡量 README 完整度。

### 应该添加

- 仓库已声明许可证时，添加许可证徽章并链接到许可证文件。
- 存在真实 CI 工作流时，添加对应分支或发布流程的构建状态徽章。
- 存在正式版本或 Release 时，添加最新版本徽章并链接到发布页。
- 存在可信覆盖率服务时，添加覆盖率徽章并链接到详细报告。
- 平台、运行时或包管理器版本是使用前提时，添加兼容性徽章。
- 下载量、包版本或服务状态对读者决策确实有帮助且存在可靠数据源时，添加对应徽章。

### 不应该添加

- 没有 CI，却使用静态 `build-passing` 徽章。
- 没有覆盖率报告，却手写覆盖率百分比。
- 项目尚未发布，却伪造版本、下载量或 Release 徽章。
- 用大量语言、编辑器、框架或“Made with love”等徽章装饰首屏。
- 添加与目标读者无关、重复正文信息或无法点击到有效详情的徽章。
- 私有、离线或内网项目无法稳定访问外部图片时，默认不使用远程徽章。

### 生成规则

- 动态状态优先使用 Shields.io 对应服务徽章；静态徽章只表达稳定事实，例如明确的平台定位。
- 默认控制在 3～6 个；信息密度高的技术项目可适当增加，但必须逐个证明价值。
- 同一 README 使用一致样式，默认 `flat-square`；只有仓库已有明确视觉规范时沿用现有样式。
- 为每个徽章提供准确的替代文本，并将徽章链接到许可证、工作流、Release、覆盖率或包页面。
- 对包含空格、连字符和特殊字符的静态徽章文本正确进行 URL 编码。
- 不暴露 Token、私有接口、内部主机名或需要鉴权的数据端点。

### 按项目选择

| 项目类型 | 常用徽章 |
|---|---|
| 应用、小程序、网站 | 许可证、构建、版本、平台 |
| 库、SDK、组件 | 包版本、下载量、构建、覆盖率、许可证、兼容性 |
| CLI、运维工具 | Release、构建、支持平台、包版本、许可证 |
| 框架、基础设施 | 构建、Release、覆盖率、镜像版本、支持平台、许可证 |
| 内部项目 | 通常不使用远程徽章；优先展示内网 CI 或部署状态链接 |

## 可选结构模块

按项目类型、读者和真实内容选择并重排模块，不为凑结构制造空章节。

1. **项目首屏**
   - Logo 或主视觉
   - 项目名称
   - 一句话定位
   - 小程序码、演示地址或下载入口（确实存在时）
   - 经“徽章决策”确认有价值的状态徽章（可选）

2. **产品简介**
   - 面向谁
   - 解决什么问题
   - 与同类方案的关键差异

3. **界面预览**
   - 3～6 张关键页面截图，或一段短演示动图
   - 按用户旅程排列，不展示重复页面

4. **核心功能**
   - 使用者能感知的能力
   - 每项说明结果，不解释内部实现

5. **使用流程**
   - 用一行流程、编号步骤或简洁 Mermaid 图说明主路径

6. **使用边界**
   - 当前不支持的关键能力
   - 隐私、安全或交易注意事项

7. **项目状态与计划**
   - 区分“已完成”“进行中”“规划中”
   - 只列用户或贡献者真正关心的里程碑

8. **开发者快速开始**
   - 环境要求
   - 安装依赖
   - 最短启动路径
   - 演示/Mock 与真实服务模式

9. **配置与部署**
   - README 保留最短可行流程
   - 复杂步骤链接到 `docs/`

10. **技术架构**
    - 一张架构图
    - 技术栈和关键边界摘要

11. **测试与质量**
    - 核心测试命令
    - 已验证范围
    - 报告或检查清单链接

12. **项目目录**
    - 只列核心目录及职责

13. **贡献、许可证与致谢**
    - 贡献入口
    - 许可证
    - 上游项目和素材来源

## 写作规则

- 首屏必须在十秒内回答：“这是什么、给谁用、有什么价值、如何体验”。
- 优先描述用户结果，不用技术名词替代产品价值。
- 不使用“最强”“完美”“企业级”等无法验证的形容词。
- 徽章只表达可验证状态，不使用静态图片制造“测试通过”“安全”或“生产就绪”的印象。
- 不暴露真实密钥、Token、私有环境 ID、个人路径或内部账号。
- 不把 AppID、客户端 ID 等公开标识误写成密钥；但公共模板应指导使用者配置自己的标识。
- 不复制完整 `docs/` 内容，不让同一说明存在两个维护源。
- 不删除仍有效的许可证、归属、兼容性和安全边界说明。

## 完成标准

- 主要读者能在首屏确认项目价值、适用性和下一步操作。
- 主要读者能沿 README 提供的最短路径成功使用、集成、运行或部署项目。
- 次要读者能快速找到属于其角色的入口，并跳转到详细文档。
- 所有功能、状态、命令、链接和图片都可由仓库事实验证。
- 所有徽章都有明确用途、可靠数据源和有效点击目标。
- README 无明显重复、过期说明、断链或未解释的占位内容。
- 修改范围聚焦 README 及必要的文档链接，不夹带无关代码变更。
