## 目标

把仓库根目录的 `README.md` 设计成面向主要读者的项目入口，而不是技术资料堆积页。README 的内容比例必须由项目类型、主要读者和首要任务决定，不使用适用于所有项目的固定比例。

## 工作流

1. **读取事实**
   - 读取现有 `README.md`、许可证、项目清单、入口配置、主要页面或模块、测试命令和 `docs/`。
   - 查找真实存在的 Logo、截图、演示图、架构图和小程序码。
   - 查找同级语言版本、语言命名约定、`SKILL.md`、Agent 元数据和客户端专用集成文件。
   - 用运行结果、配置和代码验证项目能力；不把计划功能写成已完成功能。

2. **确定读者**
   - 根据入口、清单、文档、界面和发布方式识别项目类型。
   - 明确主要读者、次要读者，以及两类读者访问 README 时最需要完成的任务。
   - 区分产品使用者、集成开发者、部署运维者、贡献者和项目维护者，不把所有技术读者统称为“开发者”。
   - 对 Agent Skill 仓库，区分开放格式能力、特定 Agent 客户端集成和可由终端调用的独立脚本；不要把三者混写为通用原生支持。
   - 无法可靠判断时，优先服务能够直接使用或集成项目的人，再服务贡献和维护人员。

3. **重组信息**
   - 按“主要读者最关心的信息 → 成功使用项目的最短路径 → 进阶配置 → 贡献与维护”排序。
   - 消费级应用、小程序和网站优先展示产品价值、界面、核心功能、使用流程与边界。
   - 库、SDK 和组件优先展示适用场景、安装、最小可运行示例、核心 API 与兼容性。
   - CLI 和运维工具优先展示安装、典型命令、输入输出、配置、权限与故障处理。
   - 框架和基础设施项目优先展示架构定位、快速开始、部署模型、兼容矩阵与运维边界。
   - 内部项目按实际角色优先级安排部署、运维、使用和开发内容。
   - 将数据库索引、完整 API、内部安全检查、长篇故障排查和详细联调步骤移入 `docs/`，README 只提供摘要与链接。

4. **编辑 README**
   - 保留仓库真实的品牌名称、许可证、致谢和必要兼容说明。
   - 使用短段落、表格、列表和一条清晰主线，避免重复标题、营销空话和大段原始日志。
   - 命令必须可复制；Windows 专用命令和跨平台命令要明确区分。
   - 图片必须有替代文本，尺寸和数量应克制，首屏避免被大量徽章占满。
   - 按“首屏排版”决定标题、徽章和语言入口的对齐方式；不要把长段正文整体居中。
   - 按“多语言文档”决定是否显示语言切换；目标文档不完整时保持单语言入口。
   - 按“徽章决策”判断是否添加 Shields.io 徽章，不把徽章作为必选装饰。

5. **验证**
   - 运行 `git diff --check -- README.md`。
   - 检查所有相对链接和本地图片目标存在。
   - 检查徽章图片 URL 与点击目标有效，徽章内容与真实数据源一致。
   - 检查每个语言入口都指向存在且完整的 README，并核对标题、命令、链接、图片、状态和使用边界是否同步。
   - 对照项目清单验证安装、启动、测试和构建命令。
   - 确认状态表与实际实现、联调结果和部署状态一致。
   - 仅修改文档时，不必运行完整代码测试；需在结果中明确说明。

## 项目类型与内容重心

以下比例仅用于帮助判断内容重心，不是硬性模板：

| 项目类型 | 主要内容 | 常见参考比例 |
|---|---|---|
| 消费级应用、小程序、网站 | 产品价值、界面、功能、使用流程 | 使用者 60%～80%，开发与维护 20%～40% |
| 开源桌面或移动应用 | 使用体验、安装、兼容性、贡献 | 使用者 50%～70%，开发与维护 30%～50% |
| 库、SDK、组件库 | 安装、示例、API、兼容性 | 集成使用 70%～90%，维护贡献 10%～30% |
| CLI、运维工具 | 安装、命令、配置、示例、故障处理 | 操作使用 60%～80%，开发维护 20%～40% |
| 框架、基础设施 | 快速开始、架构、部署、运维边界 | 技术使用 80%～90%，内部维护 10%～20% |
| 内部项目 | 按实际使用、部署、运维和开发角色确定 | 不设默认比例 |

同一项目存在多个读者群时，优先保证主要读者的最短成功路径，再为其他读者提供清晰入口或链接。

## Agent 与平台定位

仅在仓库事实支持时把项目描述为 Agent Skill，并依次判断以下边界：

1. 验证 `SKILL.md` 顶部 YAML 至少声明 `name` 和 `description`，所引用的脚本、参考资料和资源真实存在，并判断它们是否组成可复用的 Skill 核心。
2. 将 `agents/` 元数据、专用安装目录、客户端 API 或产品专属命令识别为具体客户端集成，不把它们等同于 Skill 核心。
3. 核心符合 Agent Skills 开放格式且不依赖单一客户端时，优先使用“面向 AI Agent 的 Agent Skill”或“兼容 Agent Skills 开放格式”等中性定位。
4. 仅对实际验证过的客户端写“已在 Codex 验证”“提供 Codex 集成”等有限声明；不要据此宣称支持所有 Agent 工具。
5. 对未原生加载 Agent Skills、但能运行仓库脚本的工具，说明其使用方式是终端或脚本调用，不写成原生 Skill 兼容。

如果核心工作流确实依赖某个客户端的专属 API、权限或目录结构，可以保留产品专属定位，但要明确不可移植边界。

## 首屏排版

当项目有宽幅主视觉或需要形成紧凑品牌区时，可以居中一个有限的首屏标题区，顺序优先为“项目名称 → 徽章 → 语言入口 → 主视觉”。项目简介、快速开始、表格和后续正文保持左对齐。

```html
<div align="center">
  <h1>Project Name</h1>
  <p><!-- verified badges --></p>
  <!-- 仅在所有目标语言 README 完整且能同步维护时保留下一行 -->
  <p><strong>简体中文</strong> · <a href="./README_EN.md">English</a></p>
</div>

![Project overview](./assets/project-overview.png)
```

- 即使主视觉内含项目名称，也保留一个可索引、可访问的文本一级标题。
- 没有 Logo、主视觉或紧凑首屏需求时，沿用仓库现有对齐方式，不为居中而改写结构。
- 不居中长段定位文案、功能列表、命令、表格或完整正文；居中范围应在语言入口后结束。
- 不使用多个嵌套容器或大量 `<br>` 模拟版式，确保 GitHub 与常见 Markdown 渲染器仍可读。

## 多语言文档

仅当每个目标语言 README 都已存在、内容完整且能够持续同步时显示语言切换。不要先添加入口，再留下空文件、机器直译占位或长期过期的副本。

- 沿用仓库现有命名约定；没有约定时，在 `README_EN.md`、`README.en.md` 等形式中选择一种并保持一致。
- 将语言入口放在徽章下方、主视觉或简介上方；使用语言名称，不使用国旗代替语言。
- 当前语言使用非链接强调，其他语言使用相对链接；每个语言版本都提供对称入口。
- 指定一个源语言作为事实基准，并同步标题层级、安装命令、链接、图片、能力状态、安全边界和版本要求。
- 目标文档缺失、不完整或无法维护同步时，不显示语言切换；可以把翻译列为计划，但不要制造可点击的无效承诺。

中文 README 示例：

```html
<p align="center">
  <strong>简体中文</strong> · <a href="./README_EN.md">English</a>
</p>
```

英文 README 使用相同顺序，并将 `English` 改为非链接强调、将 `简体中文` 链回中文入口。

### 创建英文 README

用户要求“创建英文自述文件”、`English README` 或中英文双语 README 时，执行完整的目标语言创建流程，不要只添加语言入口：

1. **确定基准与文件名**
   - 默认把现有根 `README.md` 作为事实基准；仓库已经声明其他源语言或维护约定时沿用该约定。
   - 沿用现有语言文件命名；没有约定时创建 `README_EN.md`，不要同时混用 `README_EN.md` 和 `README.en.md`。
   - 仓库没有任何 README 时，不假设存在中文源文档：仅要求英文时直接创建英文 `README.md`；要求双语时创建主 `README.md` 与英文 `README_EN.md`。除非用户或仓库约定另有要求，不要创建缺少 `README.md` 主入口的孤立 `README_EN.md`。
   - 创建前记录源文档的标题层级、代码围栏、折叠块、表格、相对链接、图片、徽章、命令参数和版本要求。

2. **创建完整英文版本**
   - 翻译全部标题、正文、表格、图片替代文本、`details/summary` 标签、提示词示例、代码注释、状态说明、安全边界和发布说明，不保留“待翻译”等占位。
   - 精确保留操作名、文件路径、CLI 与脚本名、参数名、模式值、URL、版本示例和事实声明；不要为了语言自然度改写可执行契约。
   - 将依赖自然语言的可执行示例本地化：英文 README 使用 `-PromptLanguage English`、英文 Conventional Commit 描述和英文发布说明；中文源文档保留对应中文示例。
   - 不凭空添加源文档没有的能力、兼容性、测试结果、版本、徽章或发布状态。

3. **添加对称导航**
   - 目标 README 完整后，才在两个文档中加入语言入口。
   - 两边使用相同语言顺序；当前语言为非链接强调，另一语言使用相对链接。
   - 中文入口应链接 `README_EN.md`，英文入口应链接回 `README.md`；链接文字使用语言名称，不使用国旗。

4. **验证内容一致性**
   - 比较两份文档的标题层级与数量、代码围栏数量与语言、表格、`details` 块、相对链接、图片目标、徽章 URL、操作名和参数集合。
   - 检查语言入口双向对称，所有本地链接和图片目标存在，英文版只保留确有必要的中文名称或示例，中文版同理。
   - 对两份文件运行 `git diff --check -- README.md README_EN.md`。新建的未跟踪文件不会出现在普通 `git diff` 内容中，必须另行读取并检查其完整内容。
   - 翻译过程中源 README 发生变化时，先把目标版本同步到最新事实；无法确认一致性时停止并说明差异，不交付过期副本。

创建或同步 README 不代表用户授权提交或推送；除非用户明确要求，否则保留两份文档供审阅。

## 徽章决策

使用 [Shields.io](https://shields.io/) 生成简洁、一致且可读的徽章。徽章必须帮助目标读者快速判断项目状态，不以数量衡量 README 完整度。

### 应该添加

- 仓库已声明许可证时，添加许可证徽章并链接到许可证文件。
- 存在真实 CI 工作流时，添加对应分支或发布流程的构建状态徽章。
- 存在正式版本或 Release 时，添加最新版本徽章并链接到发布页。
- 存在可信覆盖率服务时，添加覆盖率徽章并链接到详细报告。
- 平台、运行时或包管理器版本是使用前提时，添加兼容性徽章。
- 确认 Skill 核心符合 Agent Skills 开放格式时，可以添加 `Agent Skills Compatible` 徽章并链接到格式说明或 Skill 入口。
- PowerShell、Python、Node.js 等运行时版本是脚本执行前提时，可以添加对应运行时徽章。
- 下载量、包版本或服务状态对读者决策确实有帮助且存在可靠数据源时，添加对应徽章。

### 不应该添加

- 没有 CI，却使用静态 `build-passing` 徽章。
- 没有覆盖率报告，却手写覆盖率百分比。
- 项目尚未发布，却伪造版本、下载量或 Release 徽章。
- 用大量语言、编辑器、框架或“Made with love”等徽章装饰首屏。
- 添加与目标读者无关、重复正文信息或无法点击到有效详情的徽章。
- 仅因存在 `agents/openai.yaml` 或在 Codex 中测试过，就添加暗示跨客户端原生兼容的徽章。
- 私有、离线或内网项目无法稳定访问外部图片时，默认不使用远程徽章。

### 生成规则

- 动态状态优先使用 Shields.io 对应服务徽章；静态徽章只表达稳定事实，例如明确的平台定位。
- 默认控制在 3～6 个；信息密度高的技术项目可适当增加，但必须逐个证明价值。
- 同一 README 使用一致样式，默认 `flat-square`；只有仓库已有明确视觉规范时沿用现有样式。
- 为每个徽章提供准确的替代文本，并将徽章链接到许可证、工作流、Release、覆盖率或包页面。
- 对包含空格、连字符和特殊字符的静态徽章文本正确进行 URL 编码。
- 不暴露 Token、私有接口、内部主机名或需要鉴权的数据端点。

### 按项目选择

| 项目类型 | 常用徽章 |
|---|---|
| 应用、小程序、网站 | 许可证、构建、版本、平台 |
| 库、SDK、组件 | 包版本、下载量、构建、覆盖率、许可证、兼容性 |
| CLI、运维工具 | Release、构建、支持平台、包版本、许可证 |
| 框架、基础设施 | 构建、Release、覆盖率、镜像版本、支持平台、许可证 |
| 内部项目 | 通常不使用远程徽章；优先展示内网 CI 或部署状态链接 |

## 可选结构模块

按项目类型、读者和真实内容选择并重排模块，不为凑结构制造空章节。

1. **项目首屏**
   - Logo 或主视觉
   - 项目名称
   - 一句话定位
   - 小程序码、演示地址或下载入口（确实存在时）
   - 经“徽章决策”确认有价值的状态徽章（可选）

2. **产品简介**
   - 面向谁
   - 解决什么问题
   - 与同类方案的关键差异

3. **界面预览**
   - 3～6 张关键页面截图，或一段短演示动图
   - 按用户旅程排列，不展示重复页面

4. **核心功能**
   - 使用者能感知的能力
   - 每项说明结果，不解释内部实现

5. **使用流程**
   - 用一行流程、编号步骤或简洁 Mermaid 图说明主路径

6. **使用边界**
   - 当前不支持的关键能力
   - 隐私、安全或交易注意事项

7. **项目状态与计划**
   - 区分“已完成”“进行中”“规划中”
   - 只列用户或贡献者真正关心的里程碑

8. **开发者快速开始**
   - 环境要求
   - 安装依赖
   - 最短启动路径
   - 演示/Mock 与真实服务模式

9. **配置与部署**
   - README 保留最短可行流程
   - 复杂步骤链接到 `docs/`

10. **技术架构**
    - 一张架构图
    - 技术栈和关键边界摘要

11. **测试与质量**
    - 核心测试命令
    - 已验证范围
    - 报告或检查清单链接

12. **项目目录**
    - 只列核心目录及职责

13. **贡献、许可证与致谢**
    - 贡献入口
    - 许可证
    - 上游项目和素材来源

## 写作规则

- 首屏必须在十秒内回答：“这是什么、给谁用、有什么价值、如何体验”。
- 优先描述用户结果，不用技术名词替代产品价值。
- 不使用“最强”“完美”“企业级”等无法验证的形容词。
- 徽章只表达可验证状态，不使用静态图片制造“测试通过”“安全”或“生产就绪”的印象。
- 不暴露真实密钥、Token、私有环境 ID、个人路径或内部账号。
- 不把 AppID、客户端 ID 等公开标识误写成密钥；但公共模板应指导使用者配置自己的标识。
- 不复制完整 `docs/` 内容，不让同一说明存在两个维护源。
- 不删除仍有效的许可证、归属、兼容性和安全边界说明。

## 完成标准

- 主要读者能在首屏确认项目价值、适用性和下一步操作。
- 主要读者能沿 README 提供的最短路径成功使用、集成、运行或部署项目。
- 次要读者能快速找到属于其角色的入口，并跳转到详细文档。
- 所有功能、状态、命令、链接和图片都可由仓库事实验证。
- 所有徽章都有明确用途、可靠数据源和有效点击目标。
- Agent Skill 的开放格式能力、特定客户端集成和脚本调用边界没有被混为一谈。
- 语言入口只链接到存在、完整且与源语言保持同步的文档。
- 用户要求英文或双语 README 时，目标文档已完整创建，示例语言已本地化，双向入口和内容一致性检查均通过。
- README 无明显重复、过期说明、断链或未解释的占位内容。
- 修改范围聚焦 README 及必要的文档链接，不夹带无关代码变更。
